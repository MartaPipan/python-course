###  💻 Що таке __repr__?

Назва __repr__ походить від слова Representation (представлення).
Його головна мета — показати розробнику текстовий вигляд об'єкта, який максимально точно описує, як цей об'єкт був створений.
• Для кого це? Виключно для програмістів (для тебе, для налагодження коду, діагностики помилок та виведення в консоль/лог-файли).
• Ідеальний стандарт: Хороший __repr__ має повертати такий рядок, який можна буквально скопіювати, вставити в код і заново створити такий самий об'єкт.

Зверни увагу на прапорець !r всередині фігурних дужок ({self.name!r}). Це дуже крута фішка Python:
• Він автоматично викликає repr() для цієї змінної.
• Для рядків це означає, що вони виведуться в лапках (так, як вони пишуться в коді).

📊 Приклад без !r і з !r:

Якщо ім'я студента "Олена", а група "КН-11":
• Без !r (f"Student(name={self.name})"): виведе Student(name=Олена) — це просто текст.
• З !r (f"Student(name={self.name!r})"): виведе Student(name='Олена') — з лапками! Це одразу підказує програмісту, що перед ним саме рядок (str), а не якесь інше значення.

#### 🛡️ Безпека: чому не можна повертати паролі?

У зауваженні абсолютно правильно вказано: не повертайте чутливі дані.
Коли програма падає або записує помилки в лог-файли, вона часто автоматично викликає __repr__ для всіх активних об'єктів, щоб показати розробнику, де сталася помилка. #### ЧОМУ незмінювані дані (наприклад, тексти чи числа) можна іноді виносити як атрибути класу (наприклад, ROLE = "student"), а от змінювані (списки [], словники {}) — ні в якому разі. 
Усе зводиться до того, як саме ми працюємо з цими даними в коді: ми їх змінюємо зсередини (мутуємо) чи просто замінюємо на нові.
Ось головний секрет Python: коли ми працюємо зі змінюваними об'єктами (списки, словники), ми зазвичай модифікуємо їх за допомогою методів на кшталт .append(), .extend() або [key] = value. А коли працюємо з незмінюваними (числа, рядки), ми просто присвоюємо нове значення через знак =.
Давай розберемо, чому для незмінюваних даних атрибут класу — це безпечно.

Чому це спрацювало безпечно?

Тому що рядки не можна змінити «всередині». Коли ти пишеш olena.ROLE = "starosta", Python не міняє загальне значення класу. Він просто створює для Олени її особистий індивідуальный атрибут ROLE, який «перекриває» загальнокласовий. Загальний ROLE в класі залишається недоторканим, тому Данило та інші студенти не постраждали.

методи __repr__ та __str__ на перший погляд роблять одне й те саме — перетворюють об'єкт на текст. Але вони створені для абсолютно різної аудиторії.
Ось головна різниця в одному реченні:
• __repr__ — це текст для програмістів (для діагностики та пошуку помилок).
• __str__ — це текст для звичайних користувачів програми (гарний, зрозумілий та охайний).
Давай розберемо їх детально на життєвому прикладі.

🎭 Аналогія: Паспорт проти Візитівки

Уявімо, що наш об'єкт — це людина.
• __repr__ — це паспорт. Там усе написано чітко, офіційно, без зайвих прикрас: серія, номер, дата видачі, точне ім'я. Це інформація для «службового використання» (прикордонників чи поліції).
• __str__ — це візитівка або розповідь про себе. Там написано: "Привіт, я Марко, займаюся дизайном!". Це красива інформація для людей навколо, щоб їм було приємно та зручно читати.

1. Якщо метод __str__ відсутній:
Якщо ти не напишеш __str__, але викличеш print(olena), Python не розгубиться. Він просто візьме замість нього метод __repr__. Тому __repr__ є обов'язковим для хорошого тону, а __str__ можна додавати за бажанням, коли треба зробити виведення красивим.
2. Як викликати їх примусово:

	• repr(olena) → запустить __repr__

Щоб уникнути  пастки, у Python використовують стандартний і дуже красивий трюк: як дефолтне значення ставлять None (це незмінюваний тип даних). А вже всередині функції перевіряють: якщо прийшов None, то ми створюємо свіжий список.
python
def add_student(name, group=None):  # ПРАВИЛЬНО і безпечно!
    if group is None:
        group = []  # Організовуємо СВІЖИЙ список при кожному виклику
    
    group.append(name)
    return group

🐍 Як інкапсуляція працює в Python

В інших мовах програмування (наприклад, Java чи C++) є жорсткі замки (слова private та protected), які фізично забороняють доступ до даних.
У Python підхід інший. Творці Python вирішили, що ми всі — дорослі люди (є відома фраза в спільноті: «We are all consenting adults here»). Тому захист даних тримається на договорі та спеціальних позначках за допомогою знаків підкреслення _.
Давай подивимося на 3 рівні доступу до даних у Python.

# 1. Публічні дані (Відкриті для всіх)

Будь-яка звичайна змінна в класі є публічною. Кожен може її прочитати і змінити.
python
class BankAccount:
    def __init__(self, owner, balance):

        self.balance = balance # Публічна змінна

account = BankAccount("Марко", 1000)
account.balance = -5000000  # Катастрофа! Будь-хто ззовні може вкрасти гроші або зробити баланс від'ємним.

#  3. Приватні дані (Суворий замок: Два підкреслення __)

Якщо поставити ДВА підкреслення (наприклад, __balance), Python вмикає механізм захисту під назвою Name Mangling (спотворення імені). Він буквально ховає змінну, і якщо хтось спробує звернутися до неї ззовні, програма видасть помилку, наче такої змінної взагалі немає.
python
class BankAccount:

        self.__balance = balance # Приватна змінна. Схована на замок!

account = BankAccount("Марко", 1000)

# 🔑 Як же тоді працювати з прихованими даними? (Геттери та Сеттери)

Якщо дані сховані за двома підкресленнями __, то змінювати або читати їх можна тільки через спеціальні безпечні «кнопки» (методи) самого класу.
• Геттер (Getter) — метод, який безпечно показує значення (дозволяє подивитися на баланс).
• Сеттер (Setter) — метод, який безпечно змінює значення, перевіряючи його на правильність (як банкомат, який перевіряє, чи не намагаєшся ти зняти від'ємну суму).

🛠️ Повний правильний приклад інкапсуляції в Python:

python
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.__balance = balance # Приватне поле

    # ГЕТТЕР: Безпечно показуємо баланс
    def get_balance(self):
        return self.__balance

    # СЕТТЕР: Безпечно змінюємо баланс з перевіркою
    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Сума поповнення має бути більшою за нуль!")
        self.__balance += amount
        print(f"Рахунок успішно поповнено на {amount} грн.")

# Перевіряємо в роботі:
account = BankAccount("Марко", 1000)

# 1. Напряму зламати не вийде: account.__balance = -500 (буде помилка або створиться інша змінна)
# 2. Дивимося баланс через геттер:
print(f"Поточний баланс: {account.get_balance()} грн.") # 1000 грн.

# 3. Поповнюємо через правильний метод:
account.deposit(500)
print(f"Новий баланс: {account.get_balance()} грн.") # 1500 грн.

# 4. Спроба зробити глупість:
account.deposit(-100) # Викличе помилку ValueError! Капсула захистила дані.

📌 Головний підсумок:

Інкапсуляція потрібна для того, щоб об'єкт сам відповідав за свої дані. Ми закриваємо змінні на замок (__), щоб ніхто ззовні не міг записати туди нісенітницю, а для спілкування з об'єктом залишаємо чіткі та безпечні методи-кнопки.
В Python є ще один супер-зручний спосіб створювати геттери і сеттери, щоб не писати слова get_ та set_ вручну. Він називається декоратором @property.
""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""""
###  Декоратор @property в Python — це вершина «еволюції» геттерів та сеттерів. Він дозволяє сховати змінні під замок, але при цьому працювати з ними ззовні так красиво й просто, наче це звичайні публічні атрибути, а не методи.
По суті, @property перетворює виклик методу (функції) на звичайне звернення через крапку — без круглих дужок ().
Давай подивимося, як переписати наш попередній банківський рахунок у сучасному стилі Python.

### 🛠️ Сучасний підхід: @property та .setter

Уявімо, що ми створюємо клас для смартфона, де заряд батареї не може бути меншим за 0% або більшим за 100%.
python
class Smartphone:
    def __init__(self, model, battery_level):
        self.model = model
        self.__battery_level = battery_level # Приватна змінна

    # 1. ГЕТТЕР за допомогою @property
    # Назва методу стає назвою "віртуального" атрибута
    @property
    def battery(self):
        print("[Лог: Спрацював геттер @property]")
        return f"{self.__battery_level}%"

    # 2. СЕТТЕР за допомогою .setter
    # Назва має збігатися з назвою геттера!
    @battery.setter
    def battery(self, value):
        print(f"[Лог: Спрацював сеттер для значення {value}]")
        if not 0 <= value <= 100:
            raise ValueError("Заряд батареї має бути в межах від 0 до 100!")
        self.__battery_level = value

# 🕹️ Чому це мега-зручно? Дивимося на магію в дії:

Тепер зверни увагу на синтаксис. Ми не викликаємо функції типу get_battery() чи set_battery(50). Ми працюємо через звичайний знак рівності =, але вся валідація та захист продовжують працювати автоматично!
python
phone = Smartphone("iPhone 15", 80)

# ЧИТАННЯ ДАНИХ (працює @property):
# Зверни увагу: дужки () НЕ потрібні!
print(phone.battery)  
# Виведе: 
# [Лог: Спрацював геттер @property]
# 80%

# ЗМІНА ДАНИХ (працює @battery.setter):
# Ми просто присвоюємо число через "=", як звичайній змінній!
phone.battery = 95  
# Виведе: [Лог: Спрацював сеттер для значення 95]

print(phone.battery)  
# Виведе: 95%

# СПРОБА ЗЛАМАТИ СИСТЕМУ:
try:
    phone.battery = 150 # Перевищує 100%
except ValueError as e:
    print(f"Помилка: {e}")  
    # Виведе: Помилка: Заряд батареї має бути в межах від 0 до 100!


## 📌 Чому @property вважається правильним стилем (Pythonic Way)?

1. Ідеальний синтаксис: Код ззовні виглядає дуже чистим. Замість довгих конструкцій на кшталт student.set_score(student.get_score() + 5) ми пишемо коротко й зрозуміло: student.score += 5.
2. Зворотна сумісність: Це головна фішка! Уяви, що ти написав велику програму, де змінна score спочатку була звичайною і публічною (self.score = 50). Усі інші програмісти вже використовують твій код і пишуть print(obj.score).
Раптом правила змінилися, і тепер score треба обов'язково валідувати (перевіряти межі 0–100). Якби не було @property, тобі довелося б переписувати все на методи get_score(), і код інших програмістів зламався б.
З @property ти просто робиш змінну приватною, натомість створюєш однойменну властивість, і ні в кого ззовні код не ламається — вони продовжують писати obj.score, але тепер з автоматичною перевіркою!
